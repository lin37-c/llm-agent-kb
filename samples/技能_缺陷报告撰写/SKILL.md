# Bug 报告撰写

## 概述

一份 Bug 报告的成败 = **能否让开发者不改代码前提下 3 分钟内复现**。写 Bug 单不是描述现象，而是交付一套最小、确定、可重复的复现配方，外加清晰的影响判断。核心原则：复现步骤要让对方照做必现，预期和实际要可判定。

## 何时使用

- 需要把发现的问题提交为正式 Bug 单
- 用户给了现象让你"编/补全"一份 Bug 报告，或要你把模糊句子改写为规范 Bug
- 需要升级一个疑难问题（"挂起不处理""无法复现"）时补足关键证据

不使用：需求变更、功能建议（走需求流程）；纯 Code Review 意见。

## Bug 报告八大要素

| 要素 | 要求 |
|------|------|
| 标题 | 公式见下，一眼看懂"哪里-什么条件下-发生什么" |
| 严重度 | 对影响面的判断（见矩阵） |
| 优先级 | 处理顺序（可协商，通常同严重度挂钩） |
| 环境 | 系统/浏览器/版本/分辨率/账号角色/数据状态等外壳信息 |
| 前置条件 | 复现前必须满足的状态（登录了吗、有什么数据） |
| 复现步骤 | 有序、无歧义、从干净起点开始 |
| 预期结果 | 需求或常识告诉我们"应该怎样" |
| 实际结果 | 真实发生的现象，含报错原文 |

## 标题公式

`[模块] <条件> 触发 <现象>`
- ✅ `[登录] 连续输错 5 次后正确密码仍提示锁定且无解锁入口`
- ✅ `[收银] 订单金额含两位小数时优惠券计算金额为 0.18（应 0.2）`
- ❌ `登录有问题`（现象不明）、`系统崩溃`（无模块无触发点）

## 复现步骤的写法（核心）

1. **从干净起点开始**：写明"以 XX 账号登录"、"清空缓存"等初始动作，不用"上次那个页面"
2. **按编号分步**，每步一个动作，避免"然后随便点点"
3. **写具体数据**：输入 `<email>` + 密码 `123456`，不写"输入邮箱"
4. **每步可核对**：步骤之间读者能判断是否走对
5. **结尾给"必然结果"**：执行以上步骤后必现/概率复现（注明概率与尝试次数）
6. **最小化**：能 3 步复现就不用 8 步；去掉无关操作后仍必现则更好

## 严重度 vs 优先级

| 严重度 | 定义 | 示例 |
|--------|------|------|
| S1 致命 | 阻塞核心功能/数据丢失/安全漏洞 | 支付不扣款却发货、用户数据被他人读取 |
| S2 高 | 主要功能不可用 | 登录失败、订单无法提交 |
| S3 中 | 有替代路径可用，但异常或明显错误 | 页面报错但刷新可恢复、数据汇总差一分 |
| S4 低 | 体验/文案/样式缺陷 | 错别字、按钮错位 |

优先级 P0（立即）> P1（本迭代）> P2（下版本）> P3（择机）。严重度高不一定优先级高（如罕见环境下的致命 bug 可定为 P2 待复现确认）。

## 环境信息模板

```
- 系统/版本：macOS 14.5 / win10 22H2
- 浏览器（如适用）：Chrome 126.0，非无痕
- 应用版本：iOS 4.2.1（Build 884）
- 账号角色：普通会员（复现需会员身份）
- 网络/归属地（如相关）：5G / 华东
- 时间：2026-08-29 约 14:30
```

## 附件与证据

- 截图标注异常处；报错信息复制**原文**而非转述
- 有日志/Network 面板截图优先（时间点对齐操作步骤）
- 给出测试数据样本（如出错的那条订单号、那条 CSV 行）
- "无法稳定复现"的：附录屏/日志/概率与尝试记录，别发"偶尔报错"四个字

## 常见错误

| 错误 | 修正 |
|------|------|
| 标题只写"功能异常""页面报错" | 用公式：模块+条件+现象 |
| 步骤写"输入账号密码"不写值 | 给具体数据 |
| 混填预期与实际（"登录成功但显示错误"） | 预期=应发生；实际=真发生，分开写 |
| 报错只写"报错了" | 粘贴报错原文/截图 |
| 不写前置条件导致"复现不了" | 明确账号、数据、页面状态 |
| 无复现概率说明 | 注：必现/每 N 次 1 次/仅一次环境 |

## 检查清单（提交前）

- [ ] 标题符合"模块+条件+现象"公式，无口语化笼统词
- [ ] 若为必现问题，步骤可从零照做复现；非必现给出概率与尝试记录
- [ ] 每个输入/操作都有具体值，无"随便/正常数据"字样
- [ ] 预期结果明确可判定，实际结果含报错原文
- [ ] 严重度与优先级按矩阵给出并说明理由
- [ ] 环境信息完整（版本、账号角色、关键数据状态）
- [ ] 附件到位或说明缺失原因（截图/日志/样本数据）
