# High-priority long-term preference: model-switching trigger policy

The user explicitly requested this as a high-priority long-term preference on 2026-06-11.

Purpose:
- Make model-switching guidance concrete, timely, and stage-aware during project work.
- Cover both the ideal behavior and the current product fallback when Codex may not have direct bottom-layer model switching control.

Priority and relationship to older notes:
- Treat this note as a high-priority ad-hoc preference in the same family as the existing model-switching, workspace, and disagreement-log rules.
- When this note is relevant, prefer it over older or more generic model-switching notes because it is newer and more specific.

Two-layer behavior rule:
- Ideal target behavior: if the platform supports direct model routing or switching, Codex should proactively choose the most appropriate model by task stage, complexity, and risk without waiting for the user to manually switch.
- Current fallback behavior: if Codex cannot directly control the underlying model, Codex must explicitly tell the user when a model switch is recommended, state the recommendation strength, explain why, and note the likely downside of not switching.

Recommendation strength scale:
- `Must switch`: the current task is likely to be materially harmed by staying on a weaker/cheaper model.
- `Strongly recommend switching`: quality, reliability, or speed will likely improve enough that switching is usually worth it.
- `Recommend switching`: the stronger model is likely beneficial, but the task can still proceed on the current model with some caution.
- `No switch needed`: staying on the current lower-cost model is acceptable and aligned with efficiency.

When Codex should consider upgrading to a stronger model:
- At task description time when the user presents a multi-part, ambiguous, high-stakes, or technically deep request.
- At task start when Codex detects that the work involves architecture, system design, migration planning, security-sensitive logic, or cross-file reasoning.
- Before major decisions such as choosing an approach, committing to a refactor direction, selecting a framework, or making tradeoffs that are hard to reverse.
- Before complex code generation that spans multiple files, multiple modules, or shared abstractions.
- When debugging becomes difficult: repeated failed attempts, unclear root cause, intermittent behavior, race conditions, state corruption, environment-specific failures, or subtle regressions.
- When long-context synthesis is needed: many files, long logs, long specs, multiple competing constraints, or reconciling previous decisions with current code.
- During code review, security review, architecture review, or risk assessment, where missed nuance can be expensive.
- When the user asks for unusually high confidence, exhaustive reasoning, strong critique, edge-case enumeration, or a decision memo.
- When a task escalates midstream from simple execution into deep reasoning, for example when a quick fix turns into a structural or root-cause problem.
- When the cost of a wrong answer is high, including data loss risk, security risk, production outage risk, contract risk, or major rework risk.

Default upgrade recommendation levels:
- `Must switch`: security-sensitive review or fix, high-stakes production debugging, architecture decisions with broad blast radius, long-context root-cause analysis with repeated failed attempts, or any task where a bad answer could cause major loss or unsafe changes.
- `Strongly recommend switching`: large refactors, multi-file feature design, tricky debugging, migration planning, complex data transformations, deep code review, or dense cross-document synthesis.
- `Recommend switching`: medium-complexity implementation planning, moderately tricky bug fixing, nontrivial API integration, or a task that is not yet blocked but already feels reasoning-heavy.

When Codex should consider staying on or downgrading to a lower-cost model:
- Routine file organization, naming cleanup, summaries, rote transformations, formatting-oriented work, repetitive edits with clear patterns, or low-risk housekeeping.
- End-of-task cleanup, concise status reporting, simple documentation touch-ups, and straightforward follow-through after the key hard reasoning is already complete.
- When the task becomes repetitive after the hard decision has already been made on a stronger model.

Default lower-cost recommendation levels:
- `No switch needed`: summaries, file moves, simple edits, formatting, light Q and A, shallow triage, routine progress updates, or deterministic cleanup work.
- `Recommend switching` back down: after a difficult phase is finished and the remaining work is mostly repetitive or administrative.

Required reminder timing:
- On first read of the user request if complexity is already obviously above the current model tier.
- At the start of execution if initial exploration reveals the task is heavier than it first appeared.
- Immediately before a key decision or irreversible change.
- When the task crosses from light execution into deep reasoning.
- When repeated failure or confusion suggests the current model tier is no longer appropriate.
- When the hard phase ends and the remaining work can safely return to a cheaper model.

Required reminder content:
- Say whether the recommendation is `Must switch`, `Strongly recommend switching`, `Recommend switching`, or `No switch needed`.
- State whether the advice is to switch up, stay, or switch back down.
- Give a brief reason tied to the current task stage.
- Briefly state the likely cost of ignoring the recommendation, such as slower progress, weaker reasoning, more retries, or higher risk of a wrong decision.

Behavioral expectation:
- Codex should not stay silent when a model change is materially advisable.
- Codex should not over-recommend stronger models for obviously routine work.
- Codex should optimize for the best cost-quality tradeoff across the whole project, not for keeping one model fixed from start to finish.
